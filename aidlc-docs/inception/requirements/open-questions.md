# 検証が必要な課題

## R1. 本名・学校名などが写った写真への対策（ガードレール）

**状態**：検証中。端末だけでできる方法と、文字への規則を試作した（2026-11-12）。記録は `spikes/r1-redaction.md`。本物に近い写真をユーザーが用意する。
**Issue**：https://github.com/norihiko-takahashi/kaeriuchi/issues/1

### 難しさ
- **サーバーで見つけた時点で、画像はもう AI に渡っている。**サーバー側の検知は「保存しない」ためには使えるが、「送らない」ためには使えない。送らないためには、端末側で止める必要がある。
- 算数の文章題には、「たろうくんは りんごを3こ…」のように**登場人物の名前がよく出てくる**。これを本名と区別できないと、誤検知が多すぎて使えない。
- 手書きの日本語の名前を、端末上の軽い仕組みで見つけるのは難しい。

### 検討する方法（案）

| 層 | 方法 | 検証すること |
|---|---|---|
| 撮影の画面 | ガイド枠と案内。切り抜く範囲が大きすぎるときの注意 | 子どもが案内どおりに撮れるか（使いやすさのテスト） |
| 送る前（端末） | 顔の検知（MediaPipe など） | 端末での速さ、検知の精度 |
| 送る前（端末） | 名前などを指でなぞって塗りつぶす「かくすペン」 | 子どもが自分で使うか |
| 送る前（端末） | 端末上での文字認識（OCR）で、「なまえ」「氏名」「〇年〇組」などの欄を見つける | 手書きの文字を読み取る精度、処理の重さ |
| 解析と同時（サーバー） | AI に、個人情報の種類と場所を返させる。記名欄の名前と、問題文の登場人物を区別させる | 検知できた率、誤検知の率 |
| 解析と同時（サーバー） | 返ってきた文字に、ルールでの検知をかける（学校名、クラス、電話番号、郵便番号など） | 同上 |
| 見つかったとき | (a) 切り抜きからやり直させる / (b) 伏せ字にして先に進める | 子どもが嫌にならないか、どちらが漏れが少ないか |
| 同期のとき | 受け取った文字に、もう一度ルールでの検知をかける | 誤検知で正しいデータを止めてしまわないか |
| ニックネーム | 本名らしいときに、やさしく確認する | 判定の方法 |
| 送る前（端末） | 赤ペンの印を見つけて、枠の候補を出す（FR-2.5a）。名前の欄は、もともと枠の外になる | 照明や紙の色が違っても見つけられるか。○ と ✗・✓・／ を見分けられるか。枠の大きさの推測。古い端末での速さ |
| 逃げ道 | 端末だけで精度が足りなければ、赤い部分だけを抜き出した画像をサーバーに送る（名前は鉛筆で書くことが多いので、写らない） | 使うかどうかは、端末での結果を見て決める |

### 決まっていること（検証の結果によらない）
- 切り抜きは必須。元の写真の全体は送らない。元の写真は切り抜いたら消す。
- 画像はサーバーにも、クラウドの DB にも保存しない。
- 画像と文字の項目は、ログやエラーの記録に出さない。

### 進め方
- U3（撮影・解析）を始める前に、**検証用の短い期間（スパイク）**を設ける。
- 評価用データに、本名や学校名がわざと写ったサンプル（実在しない名前を使う）を入れ、方法ごとに「検知できた率」と「誤検知の率」を測る。
- 結果を見て、組み合わせる方法と、見つかったときの扱いを決め、US-3.3 の受け入れ基準を書く。

## R2. 撮影するのは丸付けした宿題か、丸付けしていない宿題か（前提 A1）

**状態**：未定。作りながら決める（2026-11-08 の議論）。

- 丸付けしてあれば、赤ペンを手がかりに「どこが間違いか」「正しい答えは何か」がわかる。
- 丸付けしていない場合は、AI が自分で採点するところから始まり、生成した問題と同じように、誤りのリスクが出る。
- **それまでの設計**：解析の結果に「丸付けがあったか」（`gradingMarksFound`）を入れ、ない場合は、正しい答えの確認を必須にする。両方の場合を評価用データに入れる。
- **決め方**：β版で、丸付けがある写真の割合と、ある場合とない場合それぞれの解析の精度を測る。
