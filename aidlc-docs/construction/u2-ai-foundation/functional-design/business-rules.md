# U2 機能設計：ビジネスルール（案）

数字は案です。レビューで1つずつ確認します。

## BR-U2-1 モデルの使い分け

| 役割 | 案 | 理由 |
|---|---|---|
| 解析（画像を読む） | Claude Sonnet（その時点の最新版） | 手書きの文字と赤ペンの読み取りに、高い精度が必要 |
| 問題の生成 | Claude Sonnet | 問題の質が一番大事 |
| 検証役（独自に解く） | Claude Haiku（その時点の最新版） | 作る役と別のモデルにして、同じ間違いをしにくくする。速くて安い |
| 短い文の採点 | Claude Haiku | 速さが大事 |

- モデル ID は、役割ごとに環境変数で決める（`BEDROCK_MODEL_ANALYZE` など）。
- 具体的なモデル ID は、使うアカウント・リージョンの Bedrock で使えるものを、作るときに確かめて決める。

## BR-U2-2 リージョン

- **東京リージョン（ap-northeast-1）で処理する**ことを基本にする。
- リージョンをまたぐ推論（cross-region inference）は、**初期値では使わない**。使うと、国外で処理されることがあるため（`data-inventory.md` §4）。
- 東京リージョンで使えないモデルがあるときは、レビューで相談する。

## BR-U2-3 上限

| 項目 | 案 |
|---|---|
| 画像の大きさ | 2MB まで（NFR-X1） |
| 1回の AI の呼び出しの時間切れ | 解析 20秒、生成 30秒、検証・採点 10秒 |
| やり直し | スキーマの検証の失敗と、一時的なエラー（混雑など）は、最大2回 |
| 1日の回数の上限（サーバー側） | 端末ごとに、解析 30回、生成 60回。U8 でログインができたら、保護者ごとに変える |
| 1回あたりの費用の上限 | 解析＋生成＋検証で 10円以内を目標にし、評価で測る |

## BR-U2-4 API の守り（ログインができるまで）

- U8 でログインができるまでは、`/api/ai/*` を**本番の環境では動かさない**（`APP_ENV=production` のときは 503 を返す）。ログインなしで AI を呼べると、だれでも費用を使えてしまうため。
- 開発とプレビューの環境では、回数の制限と大きさの上限だけをかける。

## BR-U2-5 記録

- 1回の呼び出しごとに、次の項目をログに出す：`requestId`、`route`、`provider`、`model`、`promptVersion`、処理時間、入力と出力のトークン数、おおよその費用（円）、結果（成功・スキーマの失敗・時間切れ・エラー）。
- **画像、問題文、子どもの答え、AI の出力の中身は、ログに出さない**（NFR-P2、L5）。
- ログは標準出力に JSON で出す（公開先に依存しない）。

## BR-U2-6 評価

- コマンド：`pnpm eval --provider mock|bedrock --suite analyze|generate`
- 結果は `evals/reports/` に Markdown と JSON で出す。前の結果と比べた差も出す。
- U2 では、評価の仕組みと、合成したサンプルを少し（教科ごとに数件）作る。本格的なデータは、`content-data-plan.md` の計画どおり、U3〜U4 で増やす。
- 評価で Bedrock を呼ぶと費用がかかるので、CI では Mock だけで動かす。Bedrock での評価は、開発者が手で動かす。
